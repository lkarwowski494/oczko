## Dni limitu: zapis i scalenie (fix 2026-10-25, P-109)
Jedna instrukcja dla trzech ścieżek: start dnia w `dodajRzad` (moduly.md, krok 3), scalenie dziennika +1 i zegarka (ADR-0008, ADR-0009) oraz synchronizacja iCloud i import „scal” (ADR-0005, ADR-0004). Wynik jest równy `scalDni()` z `docs/monetyzacja/limit.mjs` (L-20–L-20e, L-23): jedna data = jeden wiersz; dzień raz zaczęty z Pro zostaje dniem z Pro (`pro` = OR); zostaje najwcześniejszy start dnia i zdarzenie, które go zaczęło. Wiersza nigdy nie usuwa żadna z tych ścieżek (L-16). Kontrola: `sprawdz-schemat.mjs` wykonuje ten blok.
```sql
-- zapis-dnia-limitu.sql (parametry: dzien, pro, zaczeto_ms, zdarzenie_id)
INSERT INTO dzien_limitu (dzien, pro, zaczeto_ms, zdarzenie_id) VALUES (?, ?, ?, ?)
ON CONFLICT (dzien) DO UPDATE SET
  pro = max(pro, excluded.pro),
  zdarzenie_id = CASE WHEN excluded.zaczeto_ms < zaczeto_ms THEN excluded.zdarzenie_id ELSE zdarzenie_id END,
  zaczeto_ms = min(zaczeto_ms, excluded.zaczeto_ms);
```
SQLite liczy wszystkie wyrażenia `SET` na wartościach wiersza sprzed aktualizacji, więc kolejność `zdarzenie_id` i `zaczeto_ms` nie zmienia wyniku (sprawdzone w `sprawdz-schemat.mjs`: wcześniejszy start z drugiego urządzenia ustawia oba pola).

**Ostatnie +1 dla reguły pracy w toku (fix-3 2026-10-26, P-123 pkt 9; bez zmiany schematu).** `ostatniPlus` i `ostatniPlusPrzed` (`src/dane/repozytoria/liczniki.ts:64-67`, `:109-112`) czytają zdarzenia od `dzis − 2`: plan `SEARCH zdarzenie USING INDEX zdarzenie_dzien (dzien>?)`, przy 150 000 zdarzeń z 3 lat 273 wiersze w zakresie (SQLite 3.50.4, `oczko-warsztat/05-architekt/2026-10-26-fix3/dowody/pomiary.txt`; czas z laptopa nie jest budżetem). Nowy indeks po `czas_ms` niepotrzebny (kosztowałby zapis przy każdym +1). Zakres wystarcza dla każdej pary stref: reguła patrzy najwyżej `PRZERWA_NOWEGO_DNIA_MS` (1 h) wstecz, a różnica przesunięć stref wynosi najwyżej 26 h (UTC−12 … UTC+14), więc data lokalna poprzedniego +1 jest najwyżej o ⌊(26 h + 1 h) / 24 h⌋ + 1 = 2 dni wcześniejsza niż `dzis`. Warunek: przerwa < 22 h (różnica dat lokalnych < (przerwa + 26 h) / 24 h + 1; przy dłuższej zakres trzeba poszerzyć).

## Synchronizacja iCloud: skrzynka zmian (fix-7 2026-10-26, P-221 Q5a, Q6a; łatka L1)
- Tabele: `synchronizacja` (jeden wiersz `id = 1`: `wlaczona`, `wejscie`, `stan_silnika` BLOB, `nr_zmiany`) i `zmiana_icloud` (`encja`, `klucz`, `usuniete`, `nr`, `wyslano_nr`, `objete`; klucz główny `(encja, klucz)`; dwie ostatnie kolumny od M1-117, punkt niżej). Obie są stanem urządzenia: bez wyzwalaczy, poza przeniesieniem przy imporcie i przywracaniu (`przeniesienie.ts`), w kopii urządzenia tak, w archiwum `.oczko` ignorowane przy wczytaniu.
- Wyzwalacze `AFTER INSERT/UPDATE/DELETE` na 17 tabelach z `docs/architektura/icloud-tabele.json` (51), warunek `wlaczona = 1 AND wejscie = 0` (dla `ustawienie` także klucz z kolumny „iCloud = tak”). Wpis: `nr_zmiany += 1`, potem UPSERT `(encja, klucz)` z `usuniete` i `nr`. Usunięcie kaskadą zapisuje usunięcie każdego dziecka. Klucz złożony: `json_array(...)` (`rysunek`: `["<wzor_id>",<strona>]`, `projekt_wloczka`). Wyzwalacze nie nadają czasu.
- Zapisy całej bazy: „Usuń wszystkie dane” w jednej transakcji najpierw `wlaczona = 0`, `wejscie = 0`, `stan_silnika = NULL`, potem DELETE, na końcu skrzynka pusta (nic nie idzie do iCloud, P-110 Q3a). Włączenie i „Połącz z tym kontem”: pełne wpisanie wszystkich wierszy do skrzynki w jednej transakcji (moduly.md, „Kontrakt partii 7”). Wyłączenie: skrzynka pusta, dane zostają.
- **Wpis wysłany zostaje do pełnego pobrania (fix 05 p3c1 2026-11-03, M1-audytor-generalny-117, P-440 wariant (a); reguła: ADR-0005, uzupełnienie 2026-11-03; wdraża M2/08).**
  - Dwie kolumny `zmiana_icloud`, zaraz po `nr`:
    ```sql
    wyslano_nr INTEGER CHECK (wyslano_nr IS NULL OR wyslano_nr <= nr),   -- NULL = niewysłany; = nr: potwierdzony, czeka na pełne pobranie strefy (ADR-0005, uzupełnienie 2026-11-03)
    objete INTEGER NOT NULL DEFAULT 0 CHECK (objete IN (0, 1)),          -- 1 = wysłany przed początkiem bieżącego pobrania strefy; usuwany na jego udanym końcu
    ```
  - Stany: oczekujący `wyslano_nr IS NULL OR wyslano_nr < nr`, wysłany `wyslano_nr = nr`. Każdy zapis, który podnosi `nr` (wyzwalacze, `wlaczWBazie`, `odtworzWKoszu`), zwraca wpis do oczekujących, więc 51 wyzwalaczy zostaje bez zmian.
  - Zapisy (wszystkie w transakcji kolejki): potwierdzenie zapisu → `UPDATE … SET wyslano_nr = nr, objete = 0 WHERE encja = ? AND klucz = ? AND nr <= ? AND usuniete = 0`; potwierdzenie usunięcia → `DELETE … AND nr <= ? AND usuniete = 1`; początek pobrania strefy → `UPDATE zmiana_icloud SET objete = 1 WHERE wyslano_nr = nr`; udany koniec → `DELETE FROM zmiana_icloud WHERE objete = 1 AND wyslano_nr = nr`. Wyłączenie synchronizacji czyści skrzynkę jak dotąd (także wpisy wysłane).
  - **Bez migracji 0002.** Schemat v1 jest niewydany (P-110, P-184; `tests/bazy` pusty, `tests/dane/migracje-wydanych.test.ts` w stanie „brak wydanych wersji”), więc zmiana trafia razem do `schemat.sql` i `0001.sql` (test równości plików, potem `node scripts/dane/generuj-migracje.mjs`), a `WERSJA_SCHEMATU` zostaje 1. Wybrano kolumny dodawane `ADD COLUMN`, nie nową wartość `usuniete`. Nowa wartość w `CHECK` wymagałaby przebudowy tabeli (12 kroków) albo edycji `sqlite_schema`, a na tabelę `zmiana_icloud` wskazuje 51 wyzwalaczy innych tabel. Wartości startowe kolumn spełniają `CHECK` każdego istniejącego wiersza (NULL, 0). *Dlaczego:* to najprostsza zmiana, która nie rusza wyzwalaczy ani danych.
  - Warunek: jeśli przed wdrożeniem wydano build z bazą v1 (pojawi się wzorzec `tests/bazy/v1.db`), zmiana idzie jako migracja `0002.sql` (`przebudowa` nie, transakcję i `user_version = 2` daje runner, `WERSJA_SCHEMATU = 2`): `ALTER TABLE zmiana_icloud ADD COLUMN wyslano_nr INTEGER CHECK (wyslano_nr IS NULL OR wyslano_nr <= nr); ALTER TABLE zmiana_icloud ADD COLUMN objete INTEGER NOT NULL DEFAULT 0 CHECK (objete IN (0, 1));`. Istniejące wpisy stają się oczekujące, więc zostaną wysłane jeszcze raz; to bezpieczne, bo odbiór jest idempotentny (UPSERT według `zmieniono_ms`, zdarzenia `ON CONFLICT DO NOTHING`). Sprawdzone na SQLite 3.53.4 w `node:sqlite`: wiersze i `integrity_check` bez zmian, `CHECK` odrzuca `wyslano_nr > nr` (dowody p3c1).
- Zdarzenie niesie `urzadzenie` (UUID instalacji z `urzadzenie.txt`) i `urzadzenie_rodzaj` (`iphone` | `ipad`, NULL = nieznany: zegarek, ekran blokady przez dziennik; P-247 U6a, przegląd 05 2026-10-27). Oba tylko do opisu kandydatów konfliktu (F-58); kolizja treści zdarzenia (M-14) ich nie porównuje. Inwentarz: `prywatnosc.md`.
- Scalanie: `sesja` z `zmieniono_ms` (DEFAULT 0 = wiersz sprzed łatki L2, przegrywa z każdym zapisem z czasem), `zdjecie` i `obliczenie` tylko dopisywane (nie mają zapisu zmiany).
- Wzór usunięty (`wzor.usunieto_ms`, P-220 N4, kosz według P-229): znika z projektu, jest w „Ostatnio usuniętych” z przywróceniem (jak włóczka, P-209); trwałe usunięcie przez `sprzatnijKosz` (`doSprzatniecia`, dwa starty po `KOSZ_DNI`), kaskadą `rysunek`, wiersze `plik` bez odwołań; same pliki przy starcie (ADR-0001 uzupełnienie 2026-11-03).

## Polityka migracji
- Wersja w `PRAGMA user_version`; migracje to dane w `src/dane/migracje/` (`0001.sql` = `schemat.sql` v1), uruchamiane przed pierwszym zapytaniem przez runner z modułu `dane-lokalne-sqlite` (wersja w `sprawdz-schemat.mjs` jest jego odpowiednikiem dla `node:sqlite`). **Wydanej migracji nie zmieniamy**; poprawka = nowa migracja.
- Dodanie kolumny, tabeli, indeksu: zwykła migracja w transakcji. Każda inna zmiana tabeli: 12 kroków sqlite.org (`PRAGMA foreign_keys=OFF` **przed** `BEGIN`, nowa tabela, kopia, `DROP`, `RENAME new_X`, odtworzenie indeksów, `foreign_key_check` pusty, `COMMIT`, `ON`); eksperyment B (E0) pokazał, że `OFF` w transakcji nic nie robi.
- Przed migracją z przebudową: `VACUUM INTO` do `Application Support/kopie/przed-migracja-<wersja>.db`, usuwana po udanym starcie.
- **Kopia robocza (przywracanie z kopii, import archiwum) migrowana tym samym runnerem z `katalogKopii`** (fix-6 2026-10-26, N12-08, P-199): przywracanie podaje katalog tymczasowy operacji, w którym leży kopia robocza (`przed-migracja-<wersja>.db` obok niej, usuwana razem z nią); bez katalogu runner odmawia migracji z przebudową (`zapis`), więc stara kopia nie dałaby się przywrócić. Import archiwum używa portu `Migruj` z kontenera (katalog `kopie/`, sprzątany jak inne kopie). Łatka C.
- Baza nowsza niż aplikacja: odrzucona bez zmian (sprawdzone), komunikat „Zaktualizuj aplikację” (tekst: 04).
- **Kontrole bazy po migracjach** (fix 2026-10-25, Z07-15): `narzedzia/bateria-schematu.mjs` (`integralnosc`, `stanyICheck` w obie strony, `plany` z oczekiwanym indeksem każdego zapytania) sprawdza bazę zmigrowaną przez `sprawdz-schemat.mjs` i ma sprawdzać bazę zmigrowaną runnerem aplikacji (`src/dane/migracje` przez `adapter-node`, plik otwarty potem `DatabaseSync`) w teście 07/08 — dzisiejszy runner w `sprawdz-schemat.mjs` to tylko wzorzec.
- **Test na kopii każdej wydanej wersji** (rola 07): wzorzec `tests/bazy/vN.db` tworzony przy wydaniu wersji schematu N (migracje 1..N + dane brzegowe: puste napisy, NULL, wiersze podrzędne, konflikt licznika, usunięte 29 i 31 dni temu, wiersze w `poczekalnia`); wzorzec `vN.db` ma też wariant z nieprzepisanym `-wal`: trzy pliki (`.db`, `-wal`, `-shm`) skopiowane przy otwartym połączeniu z `PRAGMA wal_autocheckpoint = 0` po ostatnich zapisach (jak migawka kopii urządzenia) — migracja musi zobaczyć wiersze z `-wal`; kopia → `migruj` → liczności każdej tabeli, `integrity_check = ok`, `foreign_key_check` pusty, `user_version`, drugie uruchomienie bez zmian; przypadek negatywny (dane łamiące nowe CHECK → wycofanie całości; sprawdzone w `sprawdz-schemat.mjs`). Wersja 0.1.0 poza testem (P-070, ADR-0015).
- **Wzorzec `tests/bazy/v1.db` (aneks 08, 2026-11-03, P-306 (B), P-519):** generuje go `node --experimental-strip-types --no-warnings scripts/dane/generuj-wzorzec-v1.mjs` (migracja 1 z `src/dane/migracje/sql.ts`, dane wymyślone, stałe id i czasy; część danych tylko w `-wal`). - **Import:** weryfikacja w katalogu tymczasowym (manifest, wersje, SHA-256, miejsce) → migracja kopii do bieżącego schematu tym samym runnerem → „scal” (po UUID; zdarzenia przez `scal`, encje według `zmieniono_ms`) albo „zastąp” (najpierw `VACUUM INTO` „kopii przed importem” na 30 dni). Nowsza wersja albo zły SHA-256 → odrzucenie bez zapisu.
- **Projekt roboczy bez nazwy (fix-3 2026-10-26, P-126 (1b); wdraża 08 w partii 3, razem w `schemat.sql` i `0001.sql`):** w tabeli `projekt` po `nazwa`:
  ```sql
  nienazwany INTEGER NOT NULL DEFAULT 0 CHECK (nienazwany IN (0, 1)),   -- 1 = projekt roboczy z BR-LIC-001 „Nazwanie później”; etykieta liczona przy wyświetlaniu
  ```
  `nazwa` zostaje `NOT NULL CHECK (length(nazwa) > 0)`: projekt roboczy dostaje w niej datę startu `RRRR-MM-DD` (dzisiejsze zachowanie 08) jako wartość zapasową dla każdego miejsca, które czyta surową nazwę. Wybrano flagę zamiast `nazwa NULL`, bo `NULL` musiałby obsłużyć każdy odbiorca nazwy (lista i sortowanie `COLLATE`, stan Live Activity i zegarka — pole `nazwa: string`, eksport, „Zrób taką samą”), a pominięty odbiorca pokazałby pustkę; z flagą pominięty odbiorca pokazuje datę. Wyświetlanie (ekrany, `StanEkranuBlokady.nazwa`, `StanZegarka`): `nienazwany = 1` → `t()` z kluczem 04 i datą oraz godziną z `utworzono_ms` sformatowanymi w bieżącym języku (P-126 (1b)); `nienazwany = 0` → `nazwa`. Nadanie nazwy przez użytkownika: `nazwa` = wpis, `nienazwany = 0`, w jednej instrukcji `UPDATE`. „Zrób taką samą” z projektu roboczego: nowy projekt też `nienazwany = 1` z własną datą startu. Eksport i kopie: archiwum `.oczko` i kopie `VACUUM INTO` niosą kolumnę razem z `nazwa` (data), więc import „zastąp”/„scal” i przywrócenie odtwarzają projekt roboczy jako roboczy (etykieta liczona na urządzeniu docelowym w jego języku); przeniesienie z kopii i synchronizacja biorą kolumnę jak inne (`pragma_table_info`, `zmieniono_ms`). Nazwa pliku eksportu, karta ukończenia i zgłoszenie problemu używają etykiety, nie surowej daty. Test: projekt roboczy → etykieta w dwóch językach z tej samej daty; nadanie nazwy → flaga 0; `bateria-schematu` (CHECK 0/1). Przeszkód nie widzę; wariant zapasowy (1a) niepotrzebny.
